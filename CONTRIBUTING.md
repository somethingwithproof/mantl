# Contributing to Mantl

Read [AGENTS.md](AGENTS.md) before making changes. It records ownership boundaries,
security review requirements, and test scope. Use issues and pull requests at
[github.com/somethingwithproof/mantl](https://github.com/somethingwithproof/mantl).
Report vulnerabilities privately under [SECURITY.md](SECURITY.md).

## Setup

```sh
git clone https://github.com/somethingwithproof/mantl.git
cd mantl
mise install
```

Select and run runtimes through [mise](https://mise.jdx.dev/).
[mise.toml](mise.toml) pins Go 1.26.7, Python 3.12.12, Terraform, and validation/release
tools; [go.mod](go.mod) declares the Go 1.26.1 minimum. These tool pins are not a
claim that every target cloud supports the pinned kubectl Kubernetes version.

For Python tooling, use an isolated environment and hash-locked dependencies:

```sh
mise exec -- python -m venv .venv
mise exec -- .venv/bin/python -m pip install --only-binary :all: --require-hashes   -r requirements.txt -r requirements-test.txt
mise exec -- .venv/bin/pre-commit install
```

## Build and test

```sh
mise exec -- go build -o /tmp/mantl-main ./cmd/mantl
/tmp/mantl-main --help
mise exec -- make go-test
```

The build has a development version unless release metadata is supplied.
From the checkout, the source-built offline planning workflow is:

```sh
/tmp/mantl-main plan examples/mantl-spec.yaml --dry-run --format json
/tmp/mantl-main plan examples/mantl-spec.yaml --output-dir /tmp/mantl-generated --format json
```

The CLI also supports saved inventories, read-only comparisons, and reviewed apply;
see [planning](docs/platform-planning.md#save-and-compare-reviewed-plans).
This is generated-input verification, not approval of Terraform resource changes.

For installation on your development PATH, `mise exec -- go install ./cmd/mantl`
builds main, not the published release. Do not commit binaries or generated build
output. The [release quickstart](docs/quickstart-platform.md) is the user path.

`make go-test` is canonical. It excludes upstream chart packages under `platform/`;
**do not run `go test ./...`**. Use focused packages when changing a specific area.
For Python unit tests:

```sh
mise exec -- .venv/bin/python -m pytest tests/unit/
```

Regenerate API artifacts after changing their types or markers:

```sh
mise exec -- make manifests generate
```

Review the generated diff; never hand-edit DeepCopy files. Platform API types are
CLI inputs; only compliance CRDs are generated by `make manifests` today.
[Testing](docs/testing.md) explains disposable integration fixtures and boundaries.
[The workflow inventory](.github/workflows/README.md) is the source for CI job scope.

## Dependency locks and toolchain maintenance

Edit Python `requirements.in` inputs, then regenerate/check the complete lock set:

```sh
mise exec -- python -m ci.lock_python_dependencies
mise exec -- python -m ci.lock_python_dependencies --check
```

The resolver uses pinned uv, Python 3.12, Linux x86_64 resolution, hashes, binary-only
packages, and existing transitive pins. Root constraints feed the test lock.
Review all changed locks, including examples; regeneration contacts the package
index. Never use an unpinned `pip install -U` as the documented setup path.

For Go dependency changes, keep `go.mod`/`go.sum` consistent and run
`mise exec -- go mod verify` plus scoped tests. Keep Terraform providers and
external Actions pinned. Runtime bumps should update mise and affected CI,
container, lock, and validation contracts together. Follow existing security
review requirements for identity, encryption, compliance content, and supply chain.

## Devcontainers

The optional [.devcontainer](.devcontainer/devcontainer.json) uses the repository
Dockerfile and [.devcontainer/post-create.sh](.devcontainer/post-create.sh) to install
pinned tools, an isolated Python environment, and hooks. It mounts host Kubernetes
and cloud configuration directories; use only with a trusted checkout and review
those mounts before opening it. Setup does not create a cluster unless explicitly
requested via `CREATE_KIND_CLUSTER=true`; that path also needs a pinned kind
installation selected through mise. Container availability does not establish a
working cloud platform.

Tests can select a kubectl fixture through `MANTL_KUBECTL_PATH`; production use should
resolve a trusted kubectl binary. Keep fixtures isolated from live credentials.

## License headers

Add an SPDX license declaration to new files using the format in
[the license guide](docs/licensing.md). Preserve existing copyright and component
licenses; use companion metadata for formats that cannot carry comments. Run
`mise exec -- python -m ci.check_license_headers` before opening a PR.

## Pull requests

Keep changes focused and describe the problem, resulting behavior, validation,
and material limitations. Use Conventional Commit subjects (`feat:`, `fix:`,
`docs:`, `refactor:`, `test:`, `ci:`) because Release Please derives SemVer and
changelogs from them. Sign off commits for the repository's DCO check.

Add an ADR before changing a responsibility boundary, evidence storage contract,
test scope, or supported-cloud claim. Frameworks are reviewed YAML under
`compliance/frameworks`; controllers translate Kubernetes state into plain package
logic. Do not refactor vendored charts as Mantl code.

CI covers first-party Go/Python, generated-file drift, repository checks, Sonar,
and selected runtime/infrastructure/manifest/package jobs. A passing local/static
check does not establish cloud deployment acceptance. Run checks appropriate to
the changed area; [required checks](docs/ci-required-checks.md) explains merge gates.

## Releases

[Release Please](.github/workflows/release-please.yml) manages release PRs, versions,
and changelogs. The [release workflow](.github/workflows/release.yml) checks out an
exact validated tag, builds/signs assets, and generates provenance. Contributors
should use snapshot validation rather than publishing a release:

```sh
mise exec -- goreleaser release --snapshot --clean
```

See [release operations](docs/releases.md) for package lifecycle checks,
content-version immutability, and verification. Publishing, signing, upgrades,
and native package lifecycle tests have different prerequisites; do not infer one
from another. Never claim a SLSA level without an independent assessment.
